# DroidputterShim

## What the patches hook

Two diffs, applied against pristine upstream library sources (never checked in
as copies):

- `patches/M5GFX-0.2.27-droidputter.patch` — 8 hooks in
  `lgfx/v1/panel/Panel_LCD.cpp`: `setWindow`, `writePixels`, `writeBlock`,
  `writeImage`, `writeFillRectPreclipped`, `drawPixelPreclipped` (the
  LovyanGFX write path M5GFX is built on). Each hook tees the same call into
  `dp::` (droidputter.cpp) in addition to driving the real panel.
- `patches/M5Cardputer-1.1.1-droidputter.patch` — hooks
  `Keyboard_Class::updateKeyList` to merge USB-injected key events into the
  key list it returns, and `KeyboardReader::mutableKeyList` so the merge can
  write into the same storage the physical scan uses.

## Why a patch, not a fork

SPEC finding B: ESP32 binaries are statically linked, so the phone can't
mirror an arbitrary M5Burner `.bin`. What works is rebuilding the app against
a patched display/keyboard library — any open-source Cardputer app compiled
against the patched libs becomes a transparent phone mirror with zero source
changes. Storing diffs (not vendored copies) keeps the patch reviewable and
keeps upstream license/attribution intact.

## The overlay recipe

An app overlay is a small `platformio.ini` living outside the app's own repo
(see `apps/pense-bem/platformio.ini`):

```ini
[platformio]
src_dir = /path/to/the/unmodified/app/src
lib_extra_dirs = ../../shim/lib

[env:m5cardputer]
...
lib_deps =
    m5stack/M5Unified@0.2.20
    symlink://../../shim/lib/DroidputterShim
build_flags =
    -DDROIDPUTTER=1
    -I ../../shim/lib/DroidputterShim/src
```

`shim/apply.sh <app-dir> [<libdeps-dir>]` copies pristine M5GFX 0.2.27 +
M5Cardputer 1.1.1 into `<app-dir>/lib/` (from a libdeps dir if given, else via
`pio pkg install`) and applies both patches on top — this is what makes
PlatformIO's LDF pick up the patched libs ahead of the registry copies. The
copies under `apps/*/lib/M5GFX` and `apps/*/lib/M5Cardputer` are git-ignored
and regenerated by this script; never hand-edit them, edit the patches.

## Virtual panel (no physical display)

`shim/lib/DroidputterShim/src/dp_panel.{h,cpp}` adds `Panel_Droidputter`, an
LGFX panel with **no bus**: `setWindow`/`writePixels`/`writeBlock`/
`writeImage`/`writeFillRectPreclipped`/`drawPixelPreclipped` only feed the tee
(`dp_display.cpp`) and a static 240x135 RGB565 shadow framebuffer (built on
`lgfx::Panel_FrameBufferBase`, which already implements the framebuffer
read/write/rotate machinery — the subclass just adds the `dp::` tee calls and
plugs the static buffer into `_lines_buffer`). Width/height come from
`DROIDPUTTER_W`/`DROIDPUTTER_H` build flags (default 240x135); the panel
ignores the app's own `setRotation()` call (`Pense-Bem calls
`M5.Display.setRotation(1)` at startup like it would for real hardware) since
`panel_width`/`panel_height` are already configured as that final logical
size — honoring a runtime rotation swap would grow `_height` past the rows
the static buffer actually has.

Board selection: when built with `-DDROIDPUTTER_VIRTUAL=1`, a hook added to
`M5GFX::init_impl` (top of the function, before the NVS/autodetect dance)
constructs `Panel_Droidputter`, wires it in via `panel(p)` (the actual
pointer `LGFX_Device::init_impl` checks — `_panel_last` alone, the mistake in
the patch's first draft, only holds ownership and is never read by anyone
else), and returns early — the whole I2C/SPI board-probing autodetect() never
runs. M5Unified still initializes everything else (power, I2C, speaker if
present) normally; only the display is virtual. `_board` is set to the
closest real `board_t` (`board_M5StampS3` — a bare ESP32-S3, no display of
its own) purely for logging; nothing downstream switches on it before
`init_impl` returns.

## Version pins

- M5GFX pinned at **0.2.27**. M5Unified 0.2.21+ requires M5GFX 0.2.28, so
  M5Unified stays pinned at **0.2.20** until the patch is rebased onto
  0.2.28.
- M5Cardputer pinned at **1.1.1**.
- The patched copy's `library.json` keeps the library name `M5GFX` (and
  version `0.2.27`) unchanged so PlatformIO's LDF resolves it as a drop-in
  replacement instead of fetching the registry copy.
